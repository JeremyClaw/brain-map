Why new threads go weird

  • Short-term context lives in chat history, not in some eternal global brain.
  • Durable memory must be retrieved; it is not all preloaded every time.
  • Skills are conditional; they only load if a task clearly matches them.
  • Tool reach and approvals can differ per session or runtime.
  • Old brilliant process work is useless cross-thread if it never got promoted into docs or memory.

Message handling flow

1Message lands

Current message, metadata, runtime rules, and the present session history become the starting point.

2Session startup

Core workspace files are read first so identity, user context, and operating rules are in place.

3Task routing

I decide whether this needs memory recall, a skill, project docs, tools, approval, or just a direct answer.

4Execution

Files, browser, shell, sub-agents, or GitHub flows happen based on this session’s permissions and tool access.

What loads by default vs on demand

Default-loaded firstAlways matters
Runtime instructions, AGENTS-style startup rules, persona/voice rules, user profile, current thread history, and any explicitly injected project context.
Retrieved when neededConditional
Long-term memory search, daily notes, project/client/workflow docs, skill playbooks, archive lookups, browser inspection, repo exploration, and external fetches.
Not reliable unless documentedThe dangerous bit
Clever conclusions from old chats, temporary process state, assumptions made mid-thread, half-built workflows, and anything only ever said once in a buried conversation.

What to fix for consistency

  • Create canonical project docs for every active project.
  • Promote recurring processes into workflow notes immediately.
  • Keep daily memory notes present and current.
  • Add a routing map: “if task mentions X, read Y first”.
  • Treat chat history as temporary working memory, not long-term architecture.
